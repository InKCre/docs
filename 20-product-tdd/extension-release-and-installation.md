# Extension 分发发布与 Peer 参与契约

Extension 发布者、Registry、开发工具和宿主共同消费本契约。Registry 拥有原生产物及发布生命周期的可执行协议；宿主拥有原生加载和运行生命周期；插件拥有业务、持久数据与协作兼容。本契约通过新版 Registry、宿主及数据库协议共同交付，不能将某一 Unit 的单独升级视为部署已经完成切换。

## 插件身份与原生发布

一个 Extension Name 标识一个逻辑插件。Python、Module Federation 等 Distribution 为各自所在的 Peer 增加能力，以不同或重叠的分工参与同一插件业务。语言、仓库、迁移职责或某次调用方向不决定哪一种实现是业务中心。

一个 Native Release 由 Extension Name、Distribution 类型和该分发的精确版本共同标识。不同分发独立选择版本、构建和发布；版本相同不证明业务兼容，版本不同也不证明不兼容。平台不求解跨分发版本范围或为它们维护另一个共同产品版本。

各 producer 只构建本仓维护的原生产物，原生依赖仍通过各自包工具消费。发布候选固定本分发的源码、元数据和产物身份；重试使用保存的原候选，不以当前分支的新构建覆盖同一个坐标。宿主 SDK 条件、Python Project/Version 和 MF manifest 等格式约束由相应 Unit 校验，不成为跨分发业务兼容声明。

prepare、upload、publish 一次针对一个 Native Release。只有它自己的全部原生对象齐备时才可公开，检查与提交之间改变产物身份或关联必须重新验证。发布 Python 不等待 MF，发布 MF 不等待 Python。已发布的坐标及产物身份不可覆盖；相同请求可幂等重试，冲突需要新版本。文档不使缺少可执行产物的分发成为可安装版本。

## 随签名应用交付的原生分发

`swift_bundled` 表示宿主签名应用携带的原生分发。producer manifest 定义 Extension Name、分发格式和精确版本，由模块资源与签名应用一起交付。宿主只运行实际携带的模块，不下载动态代码、不替换精确选择；需要其他版本时明确要求更新应用。其产物供应链是签名应用，不把不存在的 Registry 发布或原生热加载能力作为已完成事实。

此分发仍有真实启停生命周期和 Peer 参与记录；应用关闭只停止实际运行，不撤回共享启用意图。未配置数据库时可离线使用扩展。首次加入与重连须区分：首次事务内创建缺失的参与，冲突则读已有值；加入或明确启用成功后，重连不重建已移除记录、不重放离线开关。用户在线明确启用可以重新创建本 Peer 的缺失参与；离线操作只改变本机运行并显示共享意图尚未更新。共享写入前复核参与选择和启用意图。Python／MF 原生产物继续按各自 Registry 发布流程交付。

## 部署共享状态与 Peer 参与

部署中一个插件只有一个逻辑身份及其共享配置、业务状态。安装选择属于 `Peer × Extension`：该 Peer 选择一种宿主支持的 Distribution 及精确版本，并保存自己的启用意图。数据库保存这些持久事实；运行端报告实际加载的分发、版本和运行结果。

| 事实 | 含义 |
| --- | --- |
| 部署 Extension 身份 | 共享显示信息、配置与业务状态，不具有统辖所有 Peer 的包版本 |
| Peer 安装选择 | 该 Peer 下次应用的精确原生分发版本，不意味着产物已经加载 |
| Peer 启用意图 | 期望该 Peer 参与，不证明进程已启动或仍在线 |
| Peer 运行事实 | 当前宿主实际完成启动的实现及版本、失败或重启需求，不能由意图推断 |

管理界面保持一个插件入口，展示它在哪些 Peer 使用。默认安装和升级作用于当前或明确选定的 Peer；批量操作需要明确目标，并分别报告结果。自动恢复使用已选择的精确版本，不追随 latest。一个 Peer 的版本更换不修改其他 Peer 的选择，包括睡眠的 Peer。

目标宿主通过新版管理协议报告自己实际支持的原生格式。离线缓存只表示最近观察；没有可靠事实时不得根据 Peer 名称、浏览器类型或应用版本猜测。纯 Python 插件可以由 Web 界面管理其他 Peer 的安装，但不能在不支持 Python 的 Web Peer 上提供可成功启用的承诺。

停用或移除某个 Peer 的参与不会删除共享配置、账号、业务状态、Source 游标或 info-base 内容。部署级删除是单独明确的操作；运行节点的停止不改变持久业务和信息的所有权。

## 业务协作与配置

各分发可直接操作已准入的共享数据库协议、解释持久图、提交工作或领取自身能够执行的 Job。确实需要另一个 Peer 执行时，才使用已有的 capability delegation。平台不把所有扩展点改为远程调用，也不为同进程每个插件建立另一份 Peer 身份和租约。

插件拥有共享配置、业务 state、Source 配置及游标、Job 参数、持久图类型和调用协议的兼容。原生发布版本只是安装坐标，不能替代这些业务契约。独立 Peer 选择允许不同版本同时参与；插件应保持必要的读写兼容，或提供明确的业务升级流程，不通过清空正常数据完成包版本变更。

配置 schema 标明产生它的精确分发来源，为选定运行端提供编辑和输入验证信息；配置数据仍属于部署。最后启动的实例不覆盖唯一的全局 schema 权威，平台不合并多份 schema 或推断所有版本都理解新配置。插件在自己接受和执行业务输入时维护对应契约。

共享业务 state 的写入对已准入原生和 PostgREST Peer 保持同一协议能力，不以当前实现位于 Core 为由建立独占写角色。合法数据形状和身份不可修改仍由协议约束，匿名调用不获此权限；插件自己的原子更新和并发保护不能被整对象覆盖替代。业务 state 可以含凭据，通用安装管理响应不因写权对等而展示其内容。

## 应用版本与失败边界

宿主在改变运行状态前校验目标坐标、发布状态、元数据、原生产物和 SDK 条件。启用成功须包含完成启动和相应副作用；持久化失败需要按宿主生命周期清理或报告真实未收敛状态。保存目标版本不等于升级完成。

显式启用和停用命令先保存参与意图，再应用运行变化；运行失败保留意图并报告实际错误，不以运行成功回调重新写入意图。自动恢复只消费已有意图，不能将用户已撤回的启用写回。宿主串行处理同一参与记录的生命周期，并在异步初始化或激活后复核精确选择与启用意图；若意图已撤回或版本已变，清理迟到实例，不将它报告为当前运行结果。该串行边界只协调当前宿主，不能排除其他已准入客户端的数据库写入，也不保证持久意图与进程状态瞬时原子切换。

离线 Peer 只能接收待应用选择，不能被宣称已停止旧实例或已运行新版。租约过期不证明进程停止。Python 等宿主若安装会修改共享原生依赖环境，应暂停该 Peer 的执行，安装后从新进程启动；只停目标插件不足以证明其他已加载依赖安全。应用失败应报告失败或待处理，不能假定自动恢复旧环境或撤销插件已经执行的业务迁移。具体进程、打包和恢复操作留在宿主本地文档。

## 历史坐标与协议迁移

Registry v2 提供独立原生分发读写。v1 只读取历史统一坐标，不将两个独立新版本拼成一个旧 Release；旧发布写入明确要求升级。历史原生产物、URL、摘要和来源可继续复用，但公开读取必须遵守对应原生发布的当前封禁与撤回状态。历史入口不能绕过新发布生命周期限制。

迁移保留旧部署身份、配置和业务状态，以及可恢复的旧安装快照。旧启用成员转为各 Peer 的参与记录，保留原精确版本及意图。缺少原生格式证据时保留待解析的旧引用，旧全局配置 schema 仅留在快照，不能被赋予未知分发的来源；新版实际宿主识别并条件更新后，才填写有来源的 schema。不得猜测格式或自动改为最新版本。原版本不存在对应分发时明确待修复，不静默选另一个版本。没有记录的停用参与历史不能补造。

新版 Extension 管理与数据库协议共同改变旧全局版本语义。切换需要新版消费者和明确的旧写入退出，不能维护两份可写版本权威。暂停活跃旧运行端、迁移数据库并启动新版宿主后，睡眠旧 Peer 返回也必须先升级；协议 revision 改变本身不停止进程。具体 schema、guard、切换和恢复步骤由数据库与宿主 owner 验证并记录。

## 验收边界

发布验收观察每种分发独立发布、缺少自身产物时保持不可公开、候选重试和提交身份一致，以及历史公开读取遵守封禁。部署验收包含精确旧版本迁移、未知分发延迟解析和非空业务 state 保留。

完整运行验收从实际 Client Web 安装入口进入目标 Peer 的启用、运行、停用和刷新恢复。一个 Peer 升级不能改变另一个同种分发 Peer 的选择；睡眠恢复、离线待应用和 Python 环境更新后的新进程也属于验收。插件案例需覆盖已有内容读取与按需执行、设置 UI 的先行运行以及共享业务数据延续。仅构建、独立 import 或调用 MF 容器不能代替实际入口验收。
