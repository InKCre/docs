# Extension Release 与安装契约

Extension 发布者、Registry 和宿主共同消费本契约。原生包构建、对象验证和宿主 SDK 兼容判断分别由对应 Unit 拥有。

## Release 身份与发布完整性

Extension Name 与精确 SemVer 标识一个 Release。Python 和 Module Federation 是同一 Release 的原生分发；各 producer 的版本与 Release 一致。分发来源、宿主 SDK 范围和产物身份仍分别记录，不能以一种格式构建成功代替另一种格式的交付。

发布者一次准备本次交付的全部原生关联，再上传对应产物，最后发布。准备请求中的实际关联表达交付计划，不增加另一份必需格式声明。Registry 只有在所有已声明关联及其原生对象齐备时才允许准备状态进入公开发布；发布资格检查与最终提交之间的关联变化不能未经检查而公开。例如，同时声明 Python 和 MF 后只上传 wheel，Release 必须保持不可安装的准备状态。只交付一种格式的 Release 仍然合法。

第一方 Extension 使用一个版本决定和一次组装发布。组装固定各 producer 的源码身份，向 producer 提供共同版本，并保存完整准备请求和产物身份。重试使用该候选的原字节，不能把当前分支的新构建当作同一个候选继续发布。Unit 的构建命令、候选存储和受保护发布流程由其部署文档拥有。

已有关联的元数据和内容身份不可覆盖。相同提交可幂等重试，冲突需要新 Release。历史已发布 Release 按实际关联读取，并继续允许合法首次补充缺失分发；不猜测或回填过去未表达的交付意图。宿主和安装流程不补偿发布者遗漏的产物。

## 部署安装与 Peer 启用

`installed` 是部署选定的精确 Release 及持久配置；`enabled` 是指定 Peer 的运行意图；`running` 是当前实例已经完成启动并应用运行副作用。这些状态不能合并。安装不启用任何 Peer，也不证明所有宿主已经下载或能够运行该 Release。

Web 管理界面可以安装纯 Python Release 供 Core 使用。启用时由目标宿主检查对应原生分发、SDK 范围和生命周期；缺少 MF 的 Release 不能在 Web Peer 本地运行。部署只有一个所选版本，版本变更影响所有 Peer，并须遵守现有全部 Peer 停用和本地运行清理约束。

## 验收边界

发布验收证明双格式缺一种时拒绝发布、产物齐备后成功、单格式发布仍可用、检查期间关联变化被拒绝，以及历史读取和合法首次补关联。完整宿主验收还须从实际安装入口进入目标 Peer 启用流程，观察运行状态和停用清理；仅构建或单独调用 MF 容器不能代替这一验收。
