# Extension 分发发布与 Peer 参与契约

Extension 的发布者通过自己的仓库交付发行。仓库的 Release 是该次公开发行的来源，部署保存各 Peer 的安装选择，宿主负责原生加载，插件负责业务和数据兼容。GitHub 是首个适用的代码托管平台。现有 Registry 发行按下文的迁移规则继续提供。

## 插件身份与原生发布

一个 Extension Name 标识一个逻辑插件。Python、Module Federation 等 Distribution 为各自所在的 Peer 增加能力，以不同或重叠的分工参与同一插件业务。语言、仓库、迁移职责或某次调用方向不决定哪一种实现是业务中心。

一个 Native Release 由 Extension Name、Distribution 类型和该分发的精确版本共同标识。不同分发独立选择版本、构建和发布；版本相同不证明业务兼容，版本不同也不证明不兼容。平台不求解跨分发版本范围或为它们维护另一个共同产品版本。

各 producer 只构建本仓维护的原生产物，原生依赖仍通过各自包工具消费。发布候选固定本分发的源码、元数据和产物身份；重试使用保存的原候选，不以当前分支的新构建覆盖同一个坐标。宿主 SDK 条件、Python Project/Version 和 MF manifest 等格式约束由相应 Unit 校验，不成为跨分发业务兼容声明。

一次发布只交付一个 Native Release。生产者在全部原生对象就绪后公开 Release。公开后的坐标和产物固定，产物变更使用新版本。Python 与 MF 各自完成发布。

共享参与协议中的 Distribution 是开放的非空字符串。各宿主报告自己支持的格式，并在实际加载边界校验。仓库独立分发首先覆盖 `python` 和 `module_federation`。

Extension 不拥有独立共享数据表。资料使用 Block／Relation／Storage，共享配置与业务状态使用已有 Extension config/state；仅本机需要的草稿、队列和运行状态保存在本机。

## 从发布者仓库发现和安装

App 可按仓库 Topic `inkcre-extension` 发现候选，也接受部署者直接提供的仓库地址。选定仓库后，从其公开 Releases 查找发行。Git tag 使用 `inkcre-ext/<namespace>/<name>/<distribution>/v<version>`，给出插件逻辑名、原生分发和精确版本。同一仓库可发布多个插件和分发类型。App 选择版本时按逻辑名与分发筛选。

GitHub Release 正文含一个机器可读的 `inkcre-release` HTML 注释。发布工具从现有生产者元数据和实际构建生成 tag 与注释里的 JSON。宿主直接读取 Releases API 返回的正文。坐标和源码提交来自 tag，产物来自 Release 附件。

```text
<!-- inkcre-release
{"schema_version":1,"source_path":"extensions/mail","host_sdk":"core-py","host_sdk_version":">=0.2.0 <0.4.0"}
-->
```

`source_path` 是源码的仓库相对目录，仓库根用 `.`。`host_sdk` 和 `host_sdk_version` 是原生包声明的 SDK 名称和兼容范围。MF 发行还包含下表的 `manifest_url`。

| 分发 | 生产者发布内容 | 宿主读取 |
| --- | --- | --- |
| `python` | 该发行的原生 wheel，作为 Release 附件 | 从附件选取兼容的 wheel，按附件摘要核对下载，并用 wheel 的原生元数据校验插件身份、版本和入口 |
| `module_federation` | 完整的 MF 资源树作为 Release 归档，同时将同样的资源树发布到该版本的静态地址 | 从描述文件中的绝对 URL `manifest_url` 加载 manifest 及其资源，静态地址支持 Web App 跨源访问和正确的内容类型 |

用户选定来源后，安装选择保存可定位该仓库与精确发行的引用。恢复时直接使用该引用，已具备对应产物时可在本机恢复。精确版本无法取得时，向用户报告该版本的错误。浏览发现和检查更新按需触发。

### First-party 发布

`InKCre/impl-py` 和 `InKCre/impl-ts` 分别在现有仓库为各自维护的 Python 与 MF 分发发布。插件仍以 `inkcre/<name>` 表达共享业务身份，App 按这个名字把两个仓库的发行显示在同一个插件入口。宿主沿用各自分发的版本和兼容范围。

以 Mail 为例，Python `0.4.0` 和 MF `0.4.4` 分别生成 `inkcre-ext/inkcre/mail/python/v0.4.0` 和 `inkcre-ext/inkcre/mail/module_federation/v0.4.4`。版本列表直接来自两个仓库的公开 Releases，普通 App 或 SDK 发行按 tag 前缀区分。

## 随签名应用交付的原生分发

`swift_bundled` 表示宿主签名应用携带的原生分发。producer manifest 定义 Extension Name、分发格式和精确版本，由模块资源与签名应用一起交付。宿主只运行实际携带的模块，不下载动态代码、不替换精确选择；需要其他版本时明确要求更新应用。其产物供应链是签名应用，不把不存在的 Registry 发布或原生热加载能力作为已完成事实。

此分发仍有真实启停生命周期和 Peer 参与记录；应用关闭只停止实际运行，不撤回共享启用意图。未配置数据库时可离线使用扩展。首次加入与重连须区分：首次事务内创建缺失的参与，冲突则读已有值；加入或明确启用成功后，重连不重建已移除记录、不重放离线开关。用户在线明确启用可以重新创建本 Peer 的缺失参与；离线操作只改变本机运行并显示共享意图尚未更新。共享写入前复核参与选择和启用意图。

## 部署共享状态与 Peer 参与

部署中一个插件只有一个逻辑身份及其共享配置、业务状态。安装选择属于 `Peer × Extension`：该 Peer 选择一种宿主支持的 Distribution 及精确版本，并保存自己的启用意图。数据库保存这些持久事实；运行端报告实际加载的分发、版本和运行结果。

| 事实 | 含义 |
| --- | --- |
| 部署 Extension 身份 | 共享显示信息、配置与业务状态，不具有统辖所有 Peer 的包版本 |
| Peer 安装选择 | 该 Peer 下次应用的精确原生分发版本，不意味着产物已经加载 |
| Peer 启用意图 | 期望该 Peer 参与，不证明进程已启动或仍在线 |
| Peer 运行事实 | 当前宿主实际完成启动的实现及版本、失败或重启需求，不能由意图推断 |

管理界面保持一个插件入口，展示它在哪些 Peer 使用。默认安装和升级作用于当前或明确选定的 Peer；批量操作需要明确目标，并分别报告结果。自动恢复使用已选择的精确版本，不追随 latest。一个 Peer 的版本更换不修改其他 Peer 的选择，包括睡眠的 Peer。

目标宿主通过新版管理协议报告自己实际支持的原生格式。离线缓存只表示最近观察；没有可靠事实时不得根据 Peer 名称、浏览器类型或应用版本猜测。纯 Python 插件可以由 Web 界面管理其他 Peer 的安装，但不能在不支持 Python 的 Web Peer 上提供可成功启用的承诺。

停用或移除某个 Peer 的参与不会删除共享配置、账号、业务状态、Source 游标或 info-base 内容。部署级删除是单独明确的操作；运行节点的停止不改变持久业务和信息的所有权。

## 业务协作与配置

各分发可直接操作已准入的共享数据库协议、解释持久图、提交工作或领取自身能够执行的 Job。确实需要另一个 Peer 执行时，才使用已有的 capability delegation。平台不把所有扩展点改为远程调用，也不为同进程每个插件建立另一份 Peer 身份和租约。

插件拥有共享配置、业务 state、Source 配置及游标、Job 参数、持久图类型和调用协议的兼容。原生发布版本只是安装坐标，不能替代这些业务契约。独立 Peer 选择允许不同版本同时参与；插件应保持必要的读写兼容，或提供明确的业务升级流程，不通过清空正常数据完成包版本变更。

配置 schema 标明产生它的精确分发来源，为选定运行端提供编辑和输入验证信息；配置数据仍属于部署。最后启动的实例不覆盖唯一的全局 schema 权威，平台不合并多份 schema 或推断所有版本都理解新配置。插件在自己接受和执行业务输入时维护对应契约。

共享业务 state 的写入对已准入原生和 PostgREST Peer 保持同一协议能力，不以当前实现位于 Core 为由建立独占写角色。合法数据形状和身份不可修改仍由协议约束，匿名调用不获此权限；插件自己的原子更新和并发保护不能被整对象覆盖替代。业务 state 可以含凭据，通用安装管理响应不因写权对等而展示其内容。

## 应用版本与失败边界

宿主在改变运行状态前校验目标坐标、发布状态、元数据、原生产物和 SDK 条件。启用成功须包含完成启动和相应副作用；持久化失败需要按宿主生命周期清理或报告真实未收敛状态。保存目标版本不等于升级完成。

针对共享参与的显式启用和停用命令先保存参与意图，再应用运行变化；运行失败保留意图并报告实际错误，不以运行成功回调重新写入意图。原生宿主的本地停用先保存本机停用状态并停止运行，再尝试更新共享意图；连接、凭据或授权错误不能阻止本机停止，也不能将共享更新报告为成功。自动恢复只消费已有意图，不能将用户已撤回的启用写回。宿主串行处理同一参与记录的生命周期，并在异步初始化或激活后复核精确选择与启用意图；若意图已撤回或版本已变，清理迟到实例，不将它报告为当前运行结果。该串行边界只协调当前宿主，不能排除其他已准入 Peer 的数据库写入，也不保证持久意图与进程状态瞬时原子切换。

离线 Peer 只能接收待应用选择，不能被宣称已停止旧实例或已运行新版。租约过期不证明进程停止。Python 等宿主若安装会修改共享原生依赖环境，应暂停该 Peer 的执行，安装后从新进程启动；只停目标插件不足以证明其他已加载依赖安全。应用失败应报告失败或待处理，不能假定自动恢复旧环境或撤销插件已经执行的业务迁移。具体进程、打包和恢复操作留在宿主本地文档。

## 历史坐标与协议迁移

Registry v2 继续提供独立原生发行。v1 只读取历史统一坐标，旧写入要求升级。Registry 提供的原有产物、URL 与文档继续遵守其撤回规则。

仓库直连发行由发布者和所用托管平台管理公开、撤回和文件可用性。现有精确选择在同一产物可经仓库来源恢复时迁移，内含旧静态地址的 MF 发行可继续使用旧入口，直到用户选择能从新来源运行的版本。旧入口在依赖它的安装完成过渡后退出。

迁移保留旧部署身份、配置和业务状态，以及可恢复的旧安装快照。旧启用成员转为各 Peer 的参与记录，保留原精确版本及意图。缺少原生格式证据时保留待解析的旧引用，旧全局配置 schema 仅留在快照，不能被赋予未知分发的来源；新版实际宿主识别并条件更新后，才填写有来源的 schema。不得猜测格式或自动改为最新版本。原版本不存在对应分发时明确待修复，不静默选另一个版本。没有记录的停用参与历史不能补造。

新版 Extension 管理与数据库协议共同改变旧全局版本语义。切换需要新版消费者和明确的旧写入退出，不能维护两份可写版本权威。暂停活跃旧运行端、迁移数据库并启动新版宿主后，睡眠旧 Peer 返回也必须先升级；协议 revision 改变本身不停止进程。具体 schema、guard、切换和恢复步骤由数据库与宿主 owner 验证并记录。

## 验收边界

以同一 first-party 插件的 Python 与 MF 为例，验证各发布者可独立交付，App 能从仓库发现或用仓库地址安装。安装和冷恢复应按记录的来源与精确版本取得产物，MF 验证实际界面和异步资源。迁移用已有 pin 验证原产物及业务数据可恢复。

完整运行验收从实际 Web 应用安装入口进入目标 Peer 的启用、运行、停用和刷新恢复。一个 Peer 升级不能改变另一个同种分发 Peer 的选择；睡眠恢复、离线待应用和 Python 环境更新后的新进程也属于验收。插件案例需覆盖已有内容读取与按需执行、设置 UI 的先行运行以及共享业务数据延续。仅构建、独立 import 或调用 MF 容器不能代替实际入口验收。
